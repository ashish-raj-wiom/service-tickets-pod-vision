01

Defining the overall objective

The target, before the current-state detail.

If the customer faces an issue, and Wiom got to know about it (via data/telemetry), both parties — customer and CSP — should be proactively communicated with, so that it does not get lost and the customer has to escalate. If the escalation does happen, Wiom should get the ticket resolved as fast as possible.

The ideal condition

IdealCustomer does not face any issue
  • Path AWiom finds out first — data / telemetry / own intelligence
    • VisionNotify both parties proactively, with an ETA — resolved before the customer needs to call
  • Path B — A missedCustomer escalates — call or app
    • FallbackResolve as fast as possible

Section 2 is 100% path B today. Path A doesn't exist — that gap drives Section 4.

Escalation-only — nothing here is proactive. Three ways in (1 IVR call · 2 customer chat · 3 Kapture agent), all converging on Ticket Service Java.

Phase 1

Ticket Creation — 3 ways in

  • 1 · IVR call — half ticket → agent picks a fixed Ticket Type + comment → full ticket. Ticket Type sets the queue; SRS only ever gets the Partner queue
  • 2 · Customer chat — classifier tags it internetIssue → self-diagnosis (plan check → open/resolved-ticket check → router ping) → only if still broken, a ticket is created
  • 3 · Kapture direct — agent creates it outright
  • All three converge on Ticket Service Java: minimal payload, no idempotency key
  • SRS then classifies independently, off its own mapping table — unrecognised text is rejected or silently redirected
Phase 2

Ticket Reaching CSP

  • SRS stamps a deadline — per-subtype, working-hours or calendar
  • TAS Restore creates the CSP's card; manages attention via 4 timers + a version counter
  • Card reaches the CSP app via a gateway that passes the subtype through untouched
  • On-screen copy is resolved client-side, from the app's own label file — not sent by any backend
  • After 12–24h of inactivity, PFT calls the CSP manually — an outbound human process, separate from SRS's own escalation ladder
Phase 3

Ticket Resolution

  • 3 resolution paths: verification-gated (default), direct-resolve (3 subtypes), direct-unresolved (reason required)
  • Automated connectivity check is advisory only — closes either way regardless of result
  • Device swap: business checks in SRS, device checks in custody service; a completed swap is the closure
Phase 4

Consequences

  • SRS signals Quality OS → CSP score, bonus, routing exposure
  • SRS is meant to tell Kapture too — no confirmed receiver found for that event
  • Reopen reuses the lineage — from Kapture (verified) or customer app (unverified)
03

Redundancies in the current system

Same job done twice, no owner on a seam, or an event with no verified receiver.

Multiple systems compute TAT, separately

  • SRS: per-subtype deadline, working/calendar clock, its own breach guard
  • Ticket Service Java: a second, independent TAT-breach system (types 3/4)
  • No evidence the two reconcile

ComplaintServiceImpl.java · WithinTatGuard.java · TicketType3Or4TatBreachHandler.java

No single source of truth for "the ticket"

  • One call → 3 IDs: Kapture ticket, SRS complaint, TAS candidate
  • Ticket → Complaint is 1:many by design (reopens)
  • "Status of this ticket" = three different answers, from three systems

01-system-map.md — ID cardinality

No clear governing body

  • SRS calls itself "the OS" — but doesn't control its own intake eligibility
  • Ticket Service Java gates who reaches SRS, and owns priority + queue outright
  • SRS has orphaned callback endpoints — an async design that was never actually wired

F-04, F-06 (03-findings.md)

Duplication logic doesn't prevent duplicates

  • No idempotency key on Ticket Service Java's create call to SRS
  • SRS skips dedup on its dominant channel, trusting Kapture is strictly 1:1
  • That assumption is false — duplicates already slip through

F-10, F-14 (03-findings.md)

Kapture edits after creation are dropped

  • Type / title / priority changes post-creation never reach SRS
  • One exception (queue → partner) creates a new complaint instead of updating the existing one

F-15 (03-findings.md)

Reopen logic — half-verified

  • Two claimed sources: Kapture (verified) and customer app (not verified)
  • Whether the customer app talks to SRS directly is still open

G-3 (04-open-questions.md)

Closure doesn't confirm round-trip

  • Kapture → CSP app: no evidence a Kapture closure reaches SRS/TAS at all
  • SRS → Kapture: resolution event has no confirmed consumer
  • One CSP action calls an SRS endpoint that doesn't exist — dead end, no error shown

G-1 (04-open-questions.md) · F-02 (03-findings.md)

Chat-origin is erased before it reaches SRS

  • Chat tickets are tagged ticket_source: CUSTOMER_CHAT — the tag stops at Ticket Service Java
  • Reopens are sent to SRS with intake_channel hardcoded to "CALL_CENTER"
  • SRS can't tell the 3 creation paths apart — "how many tickets come from chat?" is unanswerable from SRS data

F-17 (03-findings.md) · SrsClient.java:152

On re-contact, the agent is blind and the signal is lost

  • Customer calls back — agent can add a comment, but sees no ticket status, no CSP progress
  • Agent can't reach the partner either; can only apologise and point at the app
  • The app shows no live update at that moment — the comment goes nowhere

Kapture-side process — not modelled in SRS or TAS

Also found

  • Verification runs but can't block closure — for either subtype it even runs on
  • Governance docs are behind the code — a shipped, revenue feature still marked out-of-scope
  • "Intake channel" is really just a payload-shape flag, not a real signal

04

Recommendations / roadmap

Directional, not prescriptive — areas to dig into next.

Proactive communication to both parties

Before escalation

Tell both parties before either asks. SRS already has anomaly-classification scaffolding — nothing feeds it today.

During an active ticket

The CSP app can already show dynamic context on a card. Mechanism exists; the proactive trigger doesn't.

After resolution

Fix the SRS → Kapture round-trip and the customer-app reopen path first.

False resolution / verification layer

Ping data verification

Same gap — the classification exists, the feed into it doesn't.

Customer handshake

Half-built already: the CSP action and TAS state exist. Only the SRS endpoint is missing.

Reopen → consequences

A reopen is evidence of a false resolution. Check whether it reaches CSP scoring at all today.

System overhaul

One source of truth

Collapse the 3-ID problem, or formally document which ID is authoritative for what.

Explicit ownership

A real RACI across Kapture / Ticket Service / SRS / TAS.

Reliable sync

Replace fire-and-forget, no-idempotency POSTs with delivery that can be confirmed.

Outage handling

Ticket clubbing

Outages aren't linked to tickets today — one outage, many ungrouped tickets.

One-tap resolution

Needs a bulk action — TAS is entirely per-candidate today.

TAT for outages

Classification exists in SRS; nothing wires it end to end yet.
