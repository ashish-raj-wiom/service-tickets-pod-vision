01

Objective

When a customer's service breaks, Wiom should find out first, act before they have to ask, and — while it is being fixed — keep everyone able to see what is happening.

Scope. This starts the moment an issue exists. Preventing issues is network and infrastructure's mandate — we own what happens between an issue arising and it being genuinely resolved.

O1

Shrink the share of issues the customer has to report

Every ticket today begins with a customer contact. Move toward Wiom detecting the problem and acting before they need to call.

How we'd know
  • % of issues detected before customer contact
  • False-positive rate — the guardrail, not a vanity metric
  • Contacts avoided per detected issue
O2

Make the reported path shorter, and visible to everyone on it

Resolve faster — and make sure the customer, CSP and agent can all see where the ticket stands. Being unheard is a separate harm from being unresolved: a customer who can see progress isn't panicking or repeating themselves, even before the fix lands.

How we'd know
  • Median time to resolution
  • Repeat contacts per ticket · reopen rate
  • % of open tickets where all three parties can see status

Guardrail. We will not generate proactive tickets faster than they can be worked. Detection that outruns capacity moves the failure from "customer had to call" to "CSP was buried" — and a proactive ticket on a healthy connection costs real trust.

The four phases

Phase 1Creation
  • 1 · IVR half ticket → agent picks a fixed type → full ticket. Type sets the queue, and SRS only ever receives the Partner queue
  • 2 · Chat classifier → self-diagnosis (plan, existing ticket, router ping) → ticket only if still broken
  • 3 · Kapture agent creates it directly. All three post a minimal payload to SRS, which then classifies independently
Phase 2Reaching the CSP
  • SRS stamps a per-subtype deadline; TAS builds the card and manages attention via timers and a seen/unseen counter
  • On-screen copy is resolved client-side from the app's own label file — not sent by any backend
  • After 12–24h of inactivity, PFT calls the CSP manually — outbound and human, separate from SRS's escalation ladder
Phase 3Resolution
  • Three CSP-initiated routes: verification-gated (splits into system and customer triggers), direct-resolve (three subtypes only), direct-unresolved (reason required)
  • The automated connectivity check is advisory only — the ticket closes either way
  • SRS can also close with no CSP action at all — a committed device swap, or a verification timeout
Phase 4Consequences
  • SRS signals Quality OS → CSP score, bonus, routing exposure
  • The resolution does reach Kapture. Ticket Service Java receives it, fetches live Kapture state and writes back the matching sub-status
  • What does not flow is the reverse — a closure made in Kapture never reaches SRS or TAS (A-08)
  • Reopen reuses the lineage, triggered from Kapture or the customer app; both route through Ticket Service Java
03

Redundancies & anomalies

Every anomaly found so far, with an ID for reference. Severity is product impact, not code quality — Critical means something is silently wrong in production data or a customer-facing flow today.

Critical3
A-01

One ticket can become two complaints

  • Neither path is idempotent — create sends no key, and the reopen key SRS receives is discarded
  • SRS skips dedup on every ticket from Ticket Service Java, trusting Kapture is 1:1. An ordinary queue move back to Partner fires a second complaint
  • Effect: two TAT clocks, and Quality OS counts the CSP's outcome twice

F-14, F-10

A-02

Verification cannot fail a resolution

  • The connectivity check runs for a subset of subtypes, and a negative verdict still closes the ticket as resolved and system-verified
  • Effect: "verified" in our data does not mean verified

F-01

A-03

One CSP action silently does nothing

  • Offered on every in-progress card, it calls an SRS endpoint that does not exist — and the 404 is swallowed after the card has already moved to "awaiting verification"
  • The customer is never asked to verify, and the CSP is left with a card carrying zero available actions
  • Effect: the ticket can now only move via SRS's escalation path — resolved late, by someone else, rather than by the CSP who was working it

F-02

Structural8
A-04

No single source of truth for a ticket

  • One contact produces four IDs — Kapture ticket, Ticket Service Java ticket, SRS complaint, TAS candidate — each in its own store
  • Ticket → Complaint is legitimately 1:many because of reopens, so the chain is not even uniformly 1:1
  • Effect: "what is the status of this ticket" has four possible answers
A-05

Two systems compute TAT independently

  • SRS owns per-subtype deadlines on a working/calendar clock; Ticket Service Java runs a second mechanism on plain calendar arithmetic
  • Neither reads the other's deadline — verified in both directions, zero references
  • Effect: the two clocks can disagree about whether the same ticket breached
A-06

No clear governing body

  • SRS is "the OS" but does not control its own intake eligibility — Ticket Service Java decides who reaches it, and owns priority and queue outright
  • SRS carries orphaned callback endpoints from an async design that was never wired

F-04, F-06

A-07

Kapture edits after creation are dropped

  • Type, title and priority changes never reach SRS — none of the three even calls the SRS client
  • The one exception, a queue move to Partner triggered by ordinary reshuffling, creates a new complaint instead of updating

F-15

A-08

Closure syncs one way only

  • CSP resolves → Kapture updates: this works. Ticket Service Java has two intake paths (an HTTP endpoint whose payload mirrors SRS's resolution event, and a queue handler) — both fetch live Kapture state and write the right sub-status back
  • The reverse does not. Its SRS client has exactly two outbound methods, create and reopen — no close, resolve or cancel
  • And agents do occasionally resolve from Kapture. That closure never reaches SRS or TAS — so this is a live behaviour, not a theoretical hole
  • Effect: the ticket stays open on the CSP's card with its SRS clock still running, while Kapture shows it closed. He may travel to a job that no longer exists

TicketController.ResolveTicket · TicketQueueListener.handleResolveTicket · SrsClient.java

A-09

The three parties cannot see each other

  • Agent → ticket: on a callback the agent sees no status and no CSP progress, and cannot reach the partner
  • CSP → customer: no idea how many times this customer has already chased
  • Agent → CSP: availability, severity and fault clues learned on the call never reach the person fixing it
  • Ticket → customer: the app shows no live status, so calling is the only way to find out
  • Effect: the agent's entire surface is three actions — create a ticket, add a comment, occasionally mark resolve. Two of the three go nowhere: the comment reaches no one, and the resolve never leaves Kapture (A-08)
A-10

The same ticket is classified twice, in two vocabularies

  • The agent picks a Ticket Type from Kapture's fixed dropdown — and that single choice decides the queue, i.e. who works the ticket
  • SRS then re-parses the same string through its own mapping to derive class, subtype, SLA and executor — reaching the routing decision independently
  • The two vocabularies are kept aligned by hand, across three places: Kapture's dropdown, SRS's hardcoded map, and SRS's registry table
  • Effect: a disposition Kapture happily accepts can be one SRS has never heard of — rejected outright, or silently redirected, depending on a feature flag

KaptureProblemMapper · PRIMARY_CLASS_TO_EXECUTOR

A-11

Kapture is a system of record whose distinctive data never leaves it

  • Kapture holds its own ticket, and Ticket Service Java holds a separate record with its own id plus a pointer back — two stores before SRS has even been called
  • What Kapture uniquely owns — queue, priority and agent comments — reaches none of the downstream systems. SRS has no priority or queue field at all
  • Of the agent's three actions, only ticket creation propagates. The comment and the resolve stop at Kapture's boundary
  • Effect: we run a full CRM as the front door, and almost none of what it captures reaches the people doing the work

TicketEntity: ticket_id + kapture_ticket_id · SRS: zero occurrences of priority/queue

04

Roadmap

Seven areas, each tagged with the objective it serves. Item names match the anomaly they resolve, so this section reads directly against Section 03. 01–04 are repair — fixing a reported path that is broken today. 06–07 are new capability. 05 sits between them because without measurement we cannot show any of it worked.

01

Information flow

O2

Completely broken today. Once a ticket exists, none of the parties on it can see what the others are doing. A-09 alone accounts for four separate blind spots, which is why it is broken out by direction below.

Agent → ticket The agent on a callback is blind — no view of state, no idea what the CSP is doing, and no way to reach the partner. Give them the status before they have to apologise for not having it. A-09
CSP → customer The CSP does not know a customer has chased three times. That count is one of the strongest urgency signals we hold, and it stops at Kapture. A-09
Agent → CSP Availability, severity and fault clues learned on the call would help the CSP fix it faster. None of it travels today. A-09
Ticket → customer The app shows no live status, so calling is the only way to find out — the very loop we are trying to break. A-09
02

Reopen, false resolution & verification

O2

Tickets close without being fixed, and the reopen arrives as if it were a brand-new problem. Every change here moves a CSP's pay, so attribution has to be decided alongside.

Verification cannot fail a resolution A check that cannot block closure is a measurement, not a gate. Until it can fail, "verified" is not a claim we can stand behind. A-02
One CSP action silently does nothing Half-built already — the CSP action and TAS state both exist; only the SRS endpoint is missing. Building it delivers the customer handshake and stops the card going dead in the CSP's hands. A-03
A reopen should arrive as a reopen Today the CSP receives what looks like a fresh ticket and works it from scratch, instead of seeing that this customer, this fault, was already attempted. A-09
Ping-data verification The same signal that would detect a fault can confirm a fix. Pairs directly with making verification able to fail. A-02
CSP attribution rules Decide — before shipping any of the above — whether a reopen is scored against the CSP, and who owns a proactively-raised ticket. Flipping verification silently is a pay cut for the same work. decision
03

Definitions & ownership

O2

Nobody can agree on the number. Every service holds its own database, its own definitions, and its own opinion of the same ticket.

Two systems compute TAT independently SRS computes per-subtype on a working/calendar clock; Ticket Service Java computes three flat calendar buckets. The customer is told one number and the CSP is judged on another. A-05
No single source of truth for a ticket One contact produces four IDs across four stores, and Ticket → Complaint is legitimately 1:many. "How many tickets" has no single answer today. A-04
No clear governing body A real RACI across Kapture, Ticket Service, SRS and TAS. SRS is called the OS but does not control its own intake eligibility. A-06
The same ticket is classified twice, in two vocabularies Kapture's dropdown decides the queue; SRS independently re-derives class and executor from the same string. One of the two should be authoritative — today both are, and they are aligned by hand across three places. A-10
Kapture is a system of record whose distinctive data never leaves it Decide what Kapture is actually for. If queue, priority and agent comments are operationally useful, they need to travel; if they are not, we are maintaining a front door that captures data nobody downstream can act on. A-11
04

Broken linkages

O2

Data that should move between systems and does not. Each one is a concrete, bounded fix rather than a redesign.

Kapture edits after creation are dropped Type, title and priority changes made after creation never reach SRS — none of the three even calls the SRS client. A-07
Closure syncs one way only CSP resolution reaches Kapture correctly. The reverse does not — a closure made in Kapture leaves the ticket open on the CSP's card with its clock running. A-08
One ticket can become two complaints No idempotency key on create, and the reopen key SRS receives is discarded. An ordinary queue move fires a second, unlineaged complaint that Quality then counts twice. A-01
Platform takeover — verify what is wired Not greenfield: SRS emits the events, TAS consumes them, and a reason code exists. The work is confirming what actually fires in production and what is missing. verify
05

Measurement

gates both

The objective carries explicit measures. Several cannot be computed today — this has to land early or nothing above can be shown to have worked.

Record the TAT breach Ticket Service Java fires a breach notification and stores nothing — its is_sla_breach field is only ever set false. Breaches on that side are currently uncountable. A-05
Make duplicates identifiable The duplicate complaint carries no lineage, so Quality OS cannot exclude it even in principle. At minimum it needs to be detectable. A-01
Baseline the objective measures Repeat-contact rate, reopen rate by type, median resolution. Without a starting number the O1/O2 targets stay directional. O1 · O2
06

Proactive detection & comms

O1

New capability, not repair. Nothing in the system today looks for a problem before the customer reports one — this is the whole of O1, and it is worth building on a path we can already trust.

Telemetry into classification SRS already carries anomaly-classification scaffolding — the classes, executors and SLAs exist — and nothing feeds it. This is the single unlock for everything else here. new
Proactive notice to both parties Tell the customer and the CSP we believe something is wrong, with an ETA, before either has to ask. The CSP app can already render dynamic context — the trigger is what is missing. new
Detection precision A proactive ticket raised on a healthy connection costs real trust and real CSP time. False-positive rate is the number that decides whether this ships, not a footnote. guardrail
07

Outage handling

O1

Outages and service tickets are unlinked today. At scale this is where detection either pays off or buries the CSP.

Ticket clubbing One outage produces many ungrouped tickets, on a path that already skips duplicate detection. A-01
One-tap resolution Needs a bulk action; TAS is entirely per-candidate today. This is what keeps the guardrail honest — detection without it just buries the CSP. guardrail
TAT for outage-driven tickets The classification exists in SRS; nothing wires it end to end from detection to a stamped deadline. new
