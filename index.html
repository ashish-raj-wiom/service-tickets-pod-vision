01

Objective

When a customer's service breaks, Wiom should find out first, act before they have to ask, and — while it is being fixed — keep everyone able to see what is happening.

Scope. This starts the moment an issue exists. Preventing issues from happening at all is network and infrastructure's mandate, not this POD's — we own what happens between an issue arising and it being genuinely resolved.

O1

Shrink the share of issues the customer has to report

Today every single ticket begins with a customer contact. Move that toward Wiom detecting the problem and acting on it before the customer needs to call.

How we'd know
  • % of issues detected before customer contact
  • False-positive rate — the guardrail, not a vanity metric
  • Contacts avoided per detected issue
O2

Make the reported path shorter, and visible to everyone on it

Resolve faster — but also make sure the customer, the CSP and the agent can all see where the ticket stands. Being unheard is a separate harm from being unresolved: a customer who can see progress is not panicking or repeating themselves, even before the fix lands.

How we'd know
  • Median time to resolution
  • Repeat contacts per ticket
  • Reopen rate
  • % of open tickets where all three parties can see current status
Guardrail. We will not generate proactive tickets faster than they can be worked. Detection that outruns capacity moves the failure from "customer had to call" to "CSP was buried" — and a proactive ticket raised on a healthy connection costs real trust.

The two paths, once an issue exists

EntryA customer's service is broken
  • Path A · O1Wiom detects it first — telemetry, data, own intelligence
    • TargetTell both parties with an ETA, and resolve before the customer needs to call
  • Path B · O2 · A was missedThe customer reports it — call, chat, or agent
    • TargetResolve fast, and keep the customer, CSP and agent all able to see where it stands

Everything in Section 02 is Path B, and most of it is broken rather than missing — 13 code-level anomalies. Path A does not exist at all. That difference is why the roadmap tackles them in the order it does: O2 is largely fix-what's-there, O1 is new capability.

02

Current system

Escalation-only. Three ways in — IVR call, customer chat, Kapture agent — all converging on Ticket Service Java before anything reaches the CSP world.

verified in code pull, not push emitted, receiver unverified

Who owns what

ServiceOwnsDoes not own
Kapture Ticket type, queue, priority, disposition Anything past Ticket Service Java
Ticket Service Java Relay to SRS, direct customer-app serving, its own TAT-breach timer Whether it already notified SRS — no idempotency on create
SRS Classification, TAT/SLA, escalation, verification, closure, Quality OS signal Priority and queue — neither word appears anywhere in its codebase. It does not even store the ticket title
TAS Restore CSP card, allowed actions, nudge timers, timeline What the complaint means — renders whatever SRS hands it
CSP / Customer App Rendering only — CSP app resolves subtype copy client-side Any data of their own

The four phases

Phase 1Ticket Creation
  • 1 · IVR call — half ticket → agent picks a fixed Ticket Type + comment → full ticket. Ticket Type sets the queue, and SRS only ever receives the Partner queue
  • 2 · Customer chat — classifier tags it internetIssue → self-diagnosis (plan → existing ticket → router ping) → ticket only if still broken
  • 3 · Kapture direct — agent creates it outright
  • All three converge on Ticket Service Java, which posts a minimal payload to SRS
  • SRS classifies independently off its own mapping table — unrecognised text is rejected or silently redirected
Phase 2Reaching the CSP
  • SRS stamps a deadline — per-subtype, working-hours or calendar
  • TAS Restore creates the card and manages attention via timers plus a seen/unseen version counter
  • Card reaches the CSP app through a gateway that passes the subtype through untouched
  • On-screen copy is resolved client-side from the app's own label file — not sent by any backend
  • After 12–24h of inactivity, PFT calls the CSP manually — an outbound human process, separate from SRS's escalation ladder
Phase 3Resolution
  • Three CSP-initiated routes: verification-gated (which itself splits into a system and a customer trigger), direct-resolve — hard-gated to exactly three subtypes — and direct-unresolved, which requires a reason code
  • The automated connectivity check is advisory only — the ticket closes either way, with the verdict riding along as metadata
  • SRS can also close a complaint with no CSP action at all — via a committed device swap, or a customer-verification timeout
  • Device swap: business checks in SRS, device checks in the custody service; a committed swap is the closure — no verification runs after it
Phase 4Consequences
  • SRS signals Quality OS → CSP score, bonus, routing exposure
  • SRS should also inform Kapture — no confirmed receiver exists (A-08)
  • Reopen reuses the lineage and can be triggered from Kapture or the customer app; both route through Ticket Service Java
03

Redundancies & anomalies in the current system

Every anomaly found so far, with an ID so we can reference them directly. Severity is about product impact, not code quality: Critical means something is silently wrong in production data or a customer/CSP-facing flow.

Critical3 · customer or CSP impact today
A-01

One ticket can become two complaints

  • Neither path is idempotent — create sends no key, and the key the reopen path does send is silently discarded by SRS
  • SRS skips duplicate detection on every ticket arriving from Ticket Service Java, trusting Kapture is strictly 1:1
  • An ordinary queue move back to Partner — not just a resolution — fires a second, unrelated complaint
  • Effect: while the first is still open, two TAT clocks run and Quality OS counts the CSP's outcome twice

F-14, F-10 · SrsClient.java · KaptureTicketController.java

A-02

Verification cannot fail a resolution

  • The connectivity check runs for only a subset of subtypes
  • Even a negative verdict closes the ticket as resolved and system-verified
  • Effect: "verified" in our data does not mean verified

F-01 · VerificationServiceImpl.java · ResolutionFinalizer.java

A-03

One CSP action strands the ticket permanently

  • The action is offered on every in-progress card but calls an SRS endpoint that does not exist — a 404
  • The failure is swallowed after the card has already moved to "awaiting verification"
  • Effect: the CSP watches it move, then nothing ever happens — no error, no timers, no way back

F-02 · HttpSrOsAdapter.java · RestoreCandidateServiceImpl.java

Structural8 · architecture and information flow
A-04

No single source of truth for a ticket

  • One customer contact produces three IDs: Kapture ticket, SRS complaint, TAS candidate
  • Ticket → Complaint is legitimately 1:many because of reopens
  • Effect: "what is the status of this ticket" has three different answers

notes/01-system-map.md — ID cardinality

A-05

Two systems compute TAT independently

  • SRS owns per-subtype deadlines with a working/calendar clock and its own breach guard
  • Ticket Service Java runs a second mechanism on plain calendar arithmetic, covering SERVICE, OTHERS and SHIFTING tickets
  • Neither reads the other's deadline — verified in both directions, zero references
  • Effect: the two clocks can disagree about whether the same ticket breached

ComplaintServiceImpl.java · WithinTatGuard.java · TicketType3Or4TatBreachHandler.java

A-06

No clear governing body

  • SRS is described as "the OS" but does not control its own intake eligibility
  • Ticket Service Java decides who reaches SRS, and owns priority and queue outright
  • SRS carries orphaned callback endpoints from an async design that was never wired

F-04, F-06 · SrsClient.isEligibleForSrs

A-07

Kapture edits after creation are dropped

  • Type, title and priority changes made post-creation never reach SRS — none of the three even calls the SRS client
  • The one exception — a queue move to Partner, triggered by ordinary reshuffling like "pushed to queue" — creates a new complaint rather than updating the existing one

F-15 · TicketServiceImpl.java

A-08

Closure does not confirm a round trip

  • SRS emits a resolution event with no confirmed consumer anywhere
  • No evidence a Kapture-side closure ever reaches SRS or TAS
  • Effect: the two sides can disagree on whether a ticket is closed

G-1 · SrsClient.java — three methods, none of them close

A-09

Chat origin is erased before SRS sees it

  • Chat tickets carry ticket_source: CUSTOMER_CHAT — the tag stops at Ticket Service Java and is never forwarded
  • SRS labels everything CALL_CENTER, inferred from payload shape — a caller cannot override it
  • Even the titles match: the chat bot emits the same disposition strings a Kapture agent picks from
  • Effect: no field, sent or derived, separates the three paths. "How many tickets come from chat" is unanswerable from SRS data

F-17 · SrsClient.java:90-93 · SubmitComplaintRequest.java · KaptureProblemMapper.java

A-10

The customer's own words never reach anyone who can act

  • SRS consumes the problem text once at intake to derive a class, then discards it — there is no title or problem column anywhere in its schema
  • The chat path never forwards the customer's message either; the ticket title is a canned string
  • Effect: the CSP arriving on site sees a category, never what the customer actually said

ComplaintServiceImpl.java — problem is transient · CreateTicketRequest.java — no comment field

A-11

The three parties cannot see each other

  • Agent → ticket: on a callback the agent can log a comment but sees no ticket status and no CSP progress, and cannot reach the partner
  • CSP → customer: the CSP has no idea how many times this customer has already chased for the same issue
  • Agent → CSP: what the agent learns on the call — availability, severity, clues about the fault — never reaches the person who has to fix it
  • Ticket → customer: the app gives no live status either, so calling is the only way to find out
  • Effect: the customer repeats the same script every call, and the CSP works with less context than we already hold

Kapture-side process — not modelled in SRS or TAS · compounds A-10

Watch2 · known, lower urgency
A-11

Governance documents trail the code

  • A shipped, revenue-relevant feature is still marked out of scope in the locked governance doc
  • Several service docs contradict their own implementation on payloads and retry behaviour

F-05 · CX-1171 docs vs. code

A-12

Intake channel is a payload-shape flag, not a real channel

  • The field records which payload shape the caller used, not where the ticket came from
  • Compounds A-09 — the channel dimension is unreliable for analysis

04

Roadmap

Directional, not prescriptive — the areas worth going deeper on, sequenced by what unblocks what. Each links back to the anomaly it addresses.

Proactive communication to both parties

the core bet

Before escalation

Tell the customer and the CSP before either has to ask. SRS already has anomaly-classification scaffolding; nothing feeds it.

closes the Path A gap

During an active ticket

The CSP app can already show dynamic context on a card. The mechanism exists — the proactive trigger does not.

addresses A-11

After resolution

Fix the SRS → Kapture round trip first; there is little point adding comms on a loop we cannot confirm closes.

depends on A-08

Information flow

cross-party context

Ticket status for the agent

The agent on a callback is completely blind — no view of the ticket's state, no idea what the CSP is doing. Give them the status before they have to apologise for not knowing it.

addresses A-11

Repeat-contact signal to the CSP

The CSP has no idea a customer has chased three times. That count is one of the strongest urgency signals we hold, and it currently stops at Kapture.

addresses A-11

Agent intelligence to the CSP

What the agent learns on the call — when the customer is home, how severe it is, clues about the fault — would help the CSP fix it faster. Today none of it travels.

addresses A-11, A-13

Status the customer can self-serve

The app gives the customer no live view of where their issue stands — so the only way to find out is to call, which is the very loop we are trying to break.

addresses A-11

Continuity for the customer

Repeating the same script on every call is the most visible symptom of all the gaps above. Continuity is the outcome that proves the rest landed.
